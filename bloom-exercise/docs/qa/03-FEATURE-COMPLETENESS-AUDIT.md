## Source invariants

1. **Hard/Super grant is server-issued.** Renderer duration/deadline is no longer accepted as local authorization. Native requests bloom_start_enforced_credit_session and receives authoritative milliseconds.
2. **Native deadline is boot-bound.** Missing or changed boot identity denies access. Deadline is monotonic and capped to 24 hours.
3. **Retry owner is stable.** Request UUID is bound to hashed device key and requested minutes.
4. **Database starts serialize.** SQL locks bloom_settings before session/ledger checks.
5. **Easy journal writes serialize.** MacUsageStore uses flock and atomic JSON writes; interruption closes the observed interval.
6. **Unknown source flow is non-disruptive.** Missing application identity allows; recognized target browser is separately handled by host fallback.
7. **Hide request is not treated as proof.** Monitor checks isHidden/isTerminated after accepted hide call.
8. **Public key is not a server secret.** Signing/build checks reject service-role-looking key; access token is not persisted to recovery marker.

## Contradicted assumptions and missing mechanisms

- **Contradicted:** NE manager enabled means provider is live and handling traffic. Source checks configuration; no provider health signal is returned to host.
- **Contradicted:** One-second frontmost polling prevents launch bypass. The user can interact before a hide poll, and hide is best effort.
- **Contradicted:** Dedicated macOS test user isolates the current user from a content-filter system extension. Apple says system extensions run globally.
- **Contradicted:** Browser address means screen activity. It identifies the active URL, not attention/keystrokes/interaction.
- **Contradicted:** Brave Private can load a fresh `example.com` target URL while filter 1.1.1 is enabled. It loaded both before and after the monitor reported `Brave · address check: automation`. A Safari target request remained pending while enabled, then loaded after stop; without a predeclared timeout/error boundary this is inconclusive.
- **Unverified:** Safari/Brave enforcement over the complete rule lifecycle, existing connections, browser restart, and all supported protocols/settings.
- **Unverified:** Restart recovery keeps original server end and blocks until owner/expiry validation.
- **Verified in isolated SQL fixtures:** Forged client duration does not control new Easy settlement; replay settlement is idempotent. **Reported by the user:** `supabase db push` applied `20261111000001_bloom_server_timed_easy.sql` and finished successfully. **Not independently verified:** read-only linked CLI queries returned HTTP 403; the signed client could not perform a live Easy reservation/settlement because monitor coverage was unavailable.

## Theoretical complete-suite assessment

**No, because particular architectural capabilities are still unverified.** Bloom filters visible macOS flow hostnames, but Brave Private loaded a fresh configured target on notarized filter 1.1.1 even after the monitor reported the address source as automation. The exact flow was not correlated to the request. Source filter 1.1.6 adds a same-team XPC broker to pass per-user policy to the root filter, plus a narrow hostless-flow fallback based on a recent foreground-browser marker. Live macOS evidence then showed that installed 1.1.6 rejected the monitor's XPC connection because its Security.framework call omitted `kSecCSSigningInformation`, which is required for the Team ID field. Source 1.1.7 fixes the lookup; native tests and strict signing pass, but the notary Keychain profile is missing, so 1.1.7 is not installed and no browser retest has run. Blanket dropping unknown-source traffic would disrupt unrelated apps. App/permission recovery remains incomplete. Easy accounting measures server-timed elapsed access, not foreground use or uninterrupted enforcement. These gaps prevent a functional-and-reliable claim under a standard-user threat boundary.

## Decisions required before declaring completion

1. Does the product accept best-effort blocking with explicit degraded states, or require stronger guarantees across arbitrary browser/network paths?
2. The Easy policy has been selected: charge the server-timed access window continuously, including idle time. If the product instead requires proof of foreground use, a supported and independently trustworthy OS measurement mechanism is still needed.
3. What are the supported browsers and acceptable response if a browser flow cannot be identified or hiding fails?
4. What is the Tauri webview trust boundary? CSP is disabled while an authenticated renderer can invoke the native command.

Until these decisions and remediation are done, release readiness is **not ready**.
