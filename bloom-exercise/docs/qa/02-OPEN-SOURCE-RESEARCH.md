# Open-source and platform research

**Audit date:** 2026-11-11. The code references below were inspected as primary sources. Repository activity dates are a snapshot from the earlier repository metadata lookup in this task; they can change and are not a proxy for product quality.

## Apple and framework requirements

1. [Apple TN3134: Network Extension provider deployment](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment) lists a macOS content filter as a system extension from macOS 10.15, and states that system extensions run in a global context independent of the logged-in user. Bloom's minimum is 13.0. The current system-extension approach is technically compatible with a direct-distribution macOS app, subject to required entitlement, signing, approval and packaging checks.
2. [Apple content filter providers](https://developer.apple.com/documentation/networkextension/content-filter-providers) describes the two-provider control/data design and the data provider's restrictive sandbox. The data provider has **read-only** app-group access; it can inspect/filter flows but cannot write flow telemetry there. Bloom has only a data provider and host-side configuration, not a separate filter-control provider. That can be a valid simpler design, but it limits host-visible live-health signaling.
3. [Apple `NSRunningApplication.hide()`](https://developer.apple.com/documentation/appkit/nsrunningapplication/hide%28%29) describes an attempt and returns true only if hiding succeeded; [isHidden](https://developer.apple.com/documentation/appkit/nsrunningapplication/ishidden) is the observable state. Bloom's monitor now verifies that state after a run-loop turn. This remains best-effort app hiding, not process termination or tamper-proof enforcement.
4. [Tauri CSP](https://v2.tauri.app/security/csp/) says CSP is only enabled when configured and recommends a narrow policy; Bloom currently has `csp: null`. [Tauri capabilities](https://v2.tauri.app/security/capabilities/) describes window-scoped API permission configuration. Current custom Rust command validation is a useful input boundary, but does not replace CSP or prove a renderer compromise cannot invoke available commands.
5. [Tauri WebDriver overview](https://v2.tauri.app/develop/tests/webdriver/) provides a path to webview UI automation; it cannot replace actual macOS Network Extension, TCC, foreground-app, or browser traffic checks.

6. **macOS 26 URL Filter candidate:** Apple's [URL Filter API](https://developer.apple.com/documentation/networkextension/url-filters) uses a local Bloom prefilter plus a Private Information Retrieval server, Privacy Pass, and Apple's Oblivious HTTP relay. Apple's [deployment note](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment) lists URL Filter providers as app extensions on macOS 26+. Apple documents that it filters WebKit and `URLSession` requests; an app using a different network stack must voluntarily call `NEURLFilter.verdict(for:)` and honor the result. Apple's [WWDC25 session](https://developer.apple.com/videos/play/wwdc2025/234/) says distribution-signed builds require applying for Apple's OHTTP relay. This Mac is macOS 27.2.1, but Bloom has no URL Filter provider, Bloom data set, PIR service, or relay approval. This is a substantial future architecture candidate for WebKit/URLSession traffic, not an immediate Brave fix: Bloom cannot make Brave's Chromium network stack call the participation API.

## Conclusions

### iOS source audit follow-up (2026-11-11)

Bloom already uses the Family Activity picker, app and web-domain shields, category shields, app-group selection, and a Device Activity extension for expiry. The picker replaces all four shield selections when protection is active, and stop clears them. The current source template uses server-timed Easy access; elapsed access is not verified foreground use. The generated iOS extension was stale and still used usage thresholds; it has been synchronized with the template and shared elapsed-time state. Source inspection and a state fixture do not establish that authorization, delivery of expiry callbacks, shields, or recovery work on a signed iPhone. Safari and other browsers need separate device checks. Existing macOS comparisons above should not be read as an assessment of iOS enforcement.

- **Verified:** The current Apple content-filter system-extension deployment model is plausible for macOS 13+ direct distribution. It does not guarantee every browser's host is visible.
- **Verified:** `NEFilterDataProvider` is a good enforcement location for visible flow hostnames. The app-group sandbox prevents using it as a normal writable heartbeat source.
- **Verified:** Browser scripting and frontmost app APIs can support local enforcement status and browser fallback, with separate TCC permissions and per-browser tests. They are not the billing authority for Easy mode.
- **Not adopted:** PF mutation, broad packet/VPN proxying, root helpers, third-party runtime code, or copied GPL/MPL source. Each would add security/privilege/licensing cost and none cures the measured API limitations without a new architecture.
- **Verified historical result:** A 1.1.1 Brave Private test loaded the blocked `example.com` target while protection was enabled. The later privacy-safe 2026-11-12 capture logged hostless UDP allows and a broker-snapshot-unavailable allow during a Brave foreground reload, but emitted no host or source identity; it is not correlated to `example.com`.
- **Verified source change, live status pending:** Filter 1.1.10 now permits a same-user, same-boot, fresh, at-most-2.5-second cached broker snapshot for foreground browser enforcement after XPC failure. Website usage grants still require a live broker response. Native checks passed; Apple accepted and stapled the build, but its app is at sign-in, filter 1.1.9 remains active, and the 1.1.10 fallback has not run live.
- **Unverified:** Whether the Brave target flow is matched and dropped by 1.1.10, monitor-based browser hiding, Easy debit/expiry on a Mac, Calculator hiding, permission recovery, and actual restart recovery. Keep Brave enforcement marked FAIL until the target and control are retested with the 1.1.10 monitor and extension active.
