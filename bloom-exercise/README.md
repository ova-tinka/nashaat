# Bloom Exercise

Bloom Exercise is a separate app in the Nashaat repository. Expo and React Native provide the iOS and Android app; the same interface is exported to a Tauri shell for macOS. The current Nashaat color palette and navigation style are retained while Bloom's own design is pending.

## Run locally

1. Install dependencies with `npm install` in this directory.
2. Copy `.env.example` to `.env` and fill in the development Supabase URL and publishable key. A legacy anon key can be used as the publishable key. Do not use a service-role or secret key in the app.
3. Apply the Bloom migration in `../supabase/migrations` to the intended development database. The app uses its `auth.users` and existing `public.exercises` catalog.
4. Run `npm run ios`, `npm run android`, or `npm run desktop`. The desktop command requires Rust, the Tauri macOS prerequisites, and `EXPO_PUBLIC_SUPABASE_URL` in the process environment. Set the publishable key in the build environment too. The desktop wrapper uses the URL to scope its content security policy; a direct Tauri build without the wrapper cannot connect to Supabase. `npm run build:web` exports the frontend used by Tauri.

For local macOS system-extension testing, accept the Xcode license once with `sudo xcodebuild -license`. Then build with the Developer ID team so the generated app-group identifier is correct, and run the signing pass to embed the Developer ID profiles and sign the host and filter:

```sh
APPLE_SIGNING_IDENTITY='Developer ID Application: Ayham Dwairy (SSYR69RTPK)' BLOOM_TEAM_ID=SSYR69RTPK npm run desktop:build
APPLE_SIGNING_IDENTITY='Developer ID Application: Ayham Dwairy (SSYR69RTPK)' BLOOM_TEAM_ID=SSYR69RTPK npm run desktop:sign
```

`desktop:sign` expects `Bloom_macOS_Host.provisionprofile` and `Bloom_macOS_Filter.provisionprofile` in `~/Downloads` by default. Override their paths with `BLOOM_HOST_PROFILE` and `BLOOM_FILTER_PROFILE`. Test the signed `.app` at `src-tauri/target/release/bundle/macos/Bloom Exercise.app`; the DMG emitted by the build command predates this signing pass. Notarization and distribution packaging are separate steps.

### Prepare a separate macOS notarization test build

Use a confirmed non-production Supabase project and its `sb_publishable_` key. Put `BLOOM_TEST_PROJECT_REF` and `BLOOM_TEST_SUPABASE_PUBLISHABLE_KEY` in the git-ignored `.env.notary-test.local`, then run `scripts/build-macos-test.cjs` with `BLOOM_TEAM_ID` and `APPLE_SIGNING_IDENTITY` set in the process environment. The script disables Expo dotenv loading, clears inherited `EXPO_PUBLIC_` settings, checks the exported web configuration, signs the app, and creates an archive under `src-tauri/target/notary-test`. The archive contains the test project URL and publishable key; review it before submission. It is not submitted automatically. Never use a secret or service-role key.

### Test macOS with local Supabase

Start OrbStack, then run `supabase start` from the Nashaat repository root. From this directory, run `npm run desktop:build:local`. This reads the local API URL and publishable key from `supabase status`, passes them only to the build process, then signs the app. It refuses to build if the API URL is not on localhost and does not write the key into `.env`. Use the signed `.app` from the path above. Create a disposable test account in Bloom; if email confirmation is enabled, read its message in local Mailpit at `http://127.0.0.1:54324`. Supabase Studio is at `http://127.0.0.1:54323`.

The Tauri macOS host and Expo iOS app temporarily reuse the existing `com.focusflow.focusFlowFlutter` identifier. iOS also reuses the existing `com.focusflow.focusFlowFlutter.DeviceActivityMonitorExtension` identifier and `group.com.focusflow.focusFlowFlutter.shared` app group. The macOS Network Extension uses `com.focusflow.focusFlowFlutter.filter` with its matching Developer ID provisioning profile. Android remains `com.nashaat.bloomexercise`.
Expo SDK 58 requires Xcode 26.4 or later for iOS builds; see the [Expo SDK compatibility table](https://docs.expo.dev/versions/latest/). Xcode 26.2 cannot compile the installed Expo native modules.

## Implemented slice

Email sign-in and registration, the searchable exercise library with written instructions and secure demonstration links, workout-plan creation/editing/deletion, workout-session logging, weekly progress, and screen-credit settings are connected to Supabase. A library exercise can be added directly to a new workout plan. Plans can be scheduled on selected weekdays; weekly progress compares those planned slots with completed workouts and identifies unscheduled rest days. Plans and sessions store repetition, time, weight, or distance values according to exercise type. An unfinished workout can be resumed; entries are stored locally until completion. Credits default to enabled and can be disabled in Profile. Users can choose per-exercise rates or a weekly target-and-analytics strategy. Goal-based awards use a weekly pool, divide it across the target workouts, and scale each share by planned-exercise coverage, set completion, and reps/time completion; each measure is capped at the plan, and the weekly pool is enforced server-side. Workouts award a shared account balance once, and new awards expire at midnight on Sunday in the account's configured time zone. Bloom's tables are separate from Nashaat's points and social tables.

Family accounts can be linked with a one-use invitation. Parents can manage a linked child's earning rules, view weekly exercise outcomes, adjust their balance, create/edit/delete workout plans, and save blocking rules. A parent/child relationship has no age restriction. Android and macOS fetch enabled rules at sign-in, on app resume, and about once a minute while Bloom stays open. The last successfully applied targets remain local when a sync fails; account-tagged syncs are serialized so a delayed response cannot replace the current account's rules. The child cannot remove managed targets in the app. iOS rules must be selected locally through Apple's Screen Time picker because Bloom cannot map account package names or domains to Apple's opaque device tokens. Unlinking the last parent removes the server-side rules. The migrations also define Basic/Premium subscription products and entitlements, subscription records, and billing-event idempotency. Billing and ledger records are server-owned; clients cannot write them directly.

The blocking integration is native. On iOS, Bloom shows Screen Time authorization and the local target counts, then uses Apple's picker and shields for selected apps, web domains, and categories. Account-side app and domain strings still must be selected on the child's device because Apple exposes opaque local tokens. On Android, the user separately enables website checks and the Accessibility service. Bloom reads the active address locally in Chrome variants, Brave, Edge, Firefox variants, Samsung Internet, Opera, Vivaldi, and DuckDuckGo. If a recognized browser's address is unreadable, Bloom exits the whole browser; during an active Easy allowance, the full foreground-browser time is counted. Focus reports whether Android's Accessibility service is alive and asks the user to restore it if Android stops it. Android does not let Bloom silently re-enable a disabled service. Native code requires an Expo development or production build; it does not run inside Expo Go. Browser address view IDs vary by release and need physical-device verification.

Android and macOS website blocking only covers browsers Bloom recognizes and hostnames the platform exposes. Unreadable recognized browser pages are handled as whole-browser targets, which can block or charge for unrelated sites by design. In-app browsers, unsupported browsers, hidden targets, permission revocation, or a stopped native service can still reduce coverage; Bloom cannot silently restore OS permissions. Parent rule changes sync while Bloom is open and when it resumes. Changes made while it is closed wait for its next launch. The Android Accessibility service requires a prominent in-app disclosure and Google Play's accessibility declaration. Apple's device-local selection means Bloom family rules cannot be remotely enforced on iOS by string identifier; the child's Screen Time picker remains the source of iOS targets. The existing Family Controls entitlement must match the iOS app identifier and provisioning profile. AI planning, coaching and adaptation, purchases, form checking, and an aggregate outcome dashboard are not connected yet. Per-exercise rates and goal-based rewards remain unset until the user configures them. The subscription schema does not imply that purchases or payment verification are implemented.

Apple's Device Activity website-usage events cover Safari and third-party browsers that contribute web usage through `STWebpageController`; they do not establish coverage of every browser. See [Apple's DeviceActivityEvent documentation](https://developer.apple.com/documentation/deviceactivity/deviceactivityevent). Countdown monitor callbacks are delivered when the device is in use, so the iOS countdown also requires physical-device verification of reblocking behavior: [DeviceActivityCenter](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter).

The server has a shared countdown ledger for hard and super hard modes: hard permits one seventh of the week's earnings each day, and super hard applies the additional configured daily cap. Requests are serialized across devices and debit elapsed time once. Android, iOS and macOS have countdown integrations; iOS and macOS still need signed builds and real-device verification. Enforced sessions run until their scheduled end; a second device cannot stop or reuse them early. A failed or interrupted start can be retried with the same request.

Android's deadline uses elapsed device time, subtracts the server request round trip, and treats a reboot as an expired deadline. A countdown continues to charge until its scheduled end even if local access closes early, including after a reboot, sign-out, or failed device setup. It needs real-device testing; existing Android browser coverage limitations still apply.

Easy mode reserves part of the shared balance for one device and returns the unused portion when the device syncs the session. A device-specific key prevents another device from reusing or settling the reservation. A reservation that cannot be synced stays unavailable to other devices until it expires. Android measures foreground use of selected targets; a restarted device closes its local session and must sync. Website measurement has the same browser limitations as blocking. This implementation needs real-device testing, particularly for service interruptions and screen transitions.

On iOS, the monitor estimates use from Screen Time threshold callbacks. It records the latest threshold rather than partial time between callbacks and closes access if a threshold is reported impossibly early. On eligible EU installations it also requests direct usage data at settlement when the SDK and permission support it. Apple's hourly reports round the requested interval out to hour boundaries, so Bloom subtracts a pre-session baseline; changes or delays in the reported data can still affect accuracy. The direct path requires the separate Family Controls App and Website Usage capability and an SDK exposing `DeviceActivityData.activityData(filteredBy:using:)`; the locally installed iOS 26.2 SDK does not expose that method. The direct path cannot be compiled or verified with that SDK. Both paths require signed real-device testing, and Apple does not guarantee coverage of every browser. A regular Family Controls entitlement alone does not enable direct access. See [Apple's usage-data requirements](https://developer.apple.com/documentation/deviceactivity/deviceactivitydata/activitydata%28filteredby%3Ausing%3A%29) and [hourly reporting behavior](https://developer.apple.com/documentation/deviceactivity/deviceactivityfilter/segmentinterval-swift.enum/hourly%28during%3A%29).

`src-tauri/macos` contains a website-filter system extension and a background app monitor. The direct-download target now includes Apple Events usage text and the Automation entitlement; the app and monitor are not App Sandbox restricted because macOS blocks sandboxed accessibility and arbitrary Apple Events access. The release still needs the project's Developer ID signing identity, matching Network Extension/system-extension provisioning, and Apple notarization credentials. `BLOOM_TEAM_ID` (or `APPLE_TEAM_ID`) must match the app-group prefix used to build the native helper. Safari, Chrome, Edge, Brave, Arc, and Opera use active-tab Apple Events where available; Firefox and fallback reads use the browser's Accessibility address field. If a recognized browser address cannot be read, the monitor hides the browser when macOS allows it and the network filter blocks flows attributable to that browser. Easy mode charges the full foreground time of an unreadable browser. The filter only opens those flows during an active allowance when it can match the macOS source audit token to that browser; it drops unidentified flows during this fallback and warns that this can affect other apps' network activity. QUIC, encrypted ClientHello, and other unnamed flows may evade hostname checks. Signed Mac verification is still required. The iOS Family Controls entitlement does not supply macOS capabilities.

## Outcome measures

The initial five product measures are: completed workouts per active user per week; week-four workout retention; change in discretionary screen time against a user's baseline; activation to a first workout within seven days; and completion of planned weekly workouts, excluding rest days. Three additional candidates are household participation (households with both a parent and child active in a week), earned credit use (the share of earned minutes used), and workout recovery (the share of users who return to a workout within seven days after missing a planned workout).

Account-level weekly workout outcomes are shown in the app. The private SQL function `bloom_private.product_outcomes(date)` reports a completed Sunday-to-Sunday UTC week for database administrators, for example `select * from bloom_private.product_outcomes('2026-10-25');`. API roles cannot execute it. It reports workouts per workout-active user, week-four workout retention, first-workout activation within seven days of Bloom enrollment, household workout participation, and credit use for eligible expiry buckets. Cohorts that have not had enough time are marked pending, and empty cohorts have no rate. Household membership history is limited to accounts still linked at report time.

Credit use excludes expiry buckets with parent adjustments or unsettled sessions and reports when that makes the result partial or incomplete. The report marks three measures unavailable until their source data exists: comparable discretionary screen-time baselines, historical plan schedules, and missed-plan recovery after historical schedule changes. Countdown duration is not treated as actual screen use. Set targets after collecting a pilot baseline.

## Checks

See [family profiles, coaching, and competitions](docs/family-coach-competitions.md) for their deployment prerequisites, provider gates, and isolated checks.

Run `npm run typecheck`, `npm run lint`, `npx expo-doctor`, and the Expo exports for iOS, Android, and web. With Docker running, `npm run test:schema` runs the schema and access checks in a disposable PostgreSQL container with Supabase-style auth roles and a catalog fixture. It checks plan creation/editing/scheduling, rest-day progress, workout retries and rollback, rate- and target-based awards, weekly analytics, internal outcome reporting, account isolation, household subscription visibility, and billing/ledger permissions.
